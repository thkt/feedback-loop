# 分類と関連テストの接続

設定形式は[呼出し仕様](contract.md)を使う。通常checkが収集する自動テストを既定のquality集合にし、内容を確認したassuranceだけを理由付きで指定する。実サービス・手動検証等は別扱いのまま一覧へ残し、呼出し方と範囲を保つ。

qualityは要求、入出力、権限、保存、状態遷移、公開契約を確認する。assuranceは環境障害、中断・復帰、後始末、履歴保全、repo全体の整合等を主目的とする。異常系・DB・結合範囲・遅さだけでassuranceにしない。混在ファイルはqualityに残すか、必要性を確かめて分割する。意味分類をOxlintへ任せない。

`collect`は通常checkと同じ収集処理からJSON文字列配列を返す。`check:classification`でglob集合と実収集の差、重複、存在しない指定を拒否する。通常checkの対象が導入前後で減っていないことも照合する。globの誤設定と収集側の同時変更までは集合比較だけで防げない。Bunの`collect`の作り方と、一覧を実際の実行と照合する手順は[Bunのテスト一覧](collect.md)を使う。

通常runnerが許可する条件付きskipは既定で維持する。対象repoのcheckがskipを禁止している場合は`allowSkipped: false`を指定し、その失敗条件も照合する。skipを許可していても、選択した全テストがskipで一件も実行されなければ非ゼロ終了にする。package managerとrunnerは別々に確認し、npm管理のBunテストもBunで起動する。

テスト収集・準備処理とBun・Vitestは、親とのIPC接続を監視する子プロセスから起動する。直接の取消とホストによる親の強制終了で、子孫の終了と出力用pipeの解放を確認する。1秒後も残る処理は強制終了する。監視側で対象コマンドのpreloadや`.env`を重ねて読み込まず、元の環境変数がコマンドへ渡ることも照合する。監視側のstderrが切断された場合も、取消と強制終了を続ける。

`apply`時の収集も同じ監視を使う。収集の診断をstderrへ分け、`classification`のstdoutはJSONだけに保つ。収集中の取消では準備処理・テスト実行・記録更新へ進まず、次回実行で復帰できることを確認する。

## 全テストの分類

導入担当AIは収集集合の全テストファイルを読んで分類する。現行の実行単位はファイルなので、各ファイル内のテストの主目的を確認し、ファイル単位で判断する。目的の判断にhelper・fixtureの内容が必要なら、それも読む。一括移動や不要な分割を前提にしない。

assuranceへ置くファイルが対照や他のqualityファイルと重なる検査を含む場合は、混在と扱わない理由を`.feedback-loop.json`の`assurance[].reason`へ書く。

## 分類の独立評価

導入時に、分類に関わっていない新しいセッションかagentが、assuranceに指定した全ファイルを読み、指定に同意するかと根拠のテスト名・行を返す。同意しないものは導入担当が直すか、理由を添えて人の判断へ戻す。

## Bun

固定Bunの公開CLI`bun test --changed=<baseとの分岐点>`へquality候補を渡す。信頼できる記録があり、各変更の影響を対応付けできる場合に、標準選択と実行時記録・明示依存の和集合を実行する。標準選択で実行済みのファイルは重複実行せず、標準選択から漏れた補完対象を追加実行する。利用版の`--help`と実行結果を照合し、公開されていない一覧取得やdry-runのAPIを仮定しない。

スキルに同梱した記録器`scripts/record-modules.ts`を対象repoの`scripts/feedback-loop/`へ配置し、通常のモジュール読込み、JSON・非ASCII・動的import・子Bunの帰属を再利用する。quality候補を一度の`bun test --changed --isolate`へ渡し、未実行の補完対象だけを追加する。Bunの実行版は対象repoの固定runtimeを使い、`prepare`を一度完了してからテストを起動する。分類検査では準備を行わない。

`bunWorkers`でBun標準のworker数を指定する。省略時は4、1なら直列とし、補完と全qualityへのfallbackにも同じ設定を使う。`bunArgs`と`testArgs`の既存引数を保ち、隔離と並列の指定はこの接続へ集約する。`--isolate`はファイルごとにglobalとmodule cacheを分離するが、workerのOSプロセスは再利用する。導入時には対象repoの全qualityを実行し、ファイル別の完了と記録の帰属、並列実行との互換性を確認する。

JUnitのファイル別結果と記録されたownerを照合し、読み込んだファイルの結果欠落や0件を成功にしない。補完と全件実行では指定した全ファイルの完了を要求する。失敗・取消では起動した処理の終了を待ち、部分成功の記録を採用しない。終了や結果が確定しない候補は、利用中の依存記録から外す。導入時の小さい対照で、この経路と既存のskip条件を確認する。

テストを起動するBunには`--no-orphans`を付け、ホストが親を強制終了した場合もleader・workerを残さない。直接の取消に加え、ホストの取消・タイムアウトによる子孫の終了と出力用pipeの解放を確認する。中断後も比較元との分岐点からの変更一覧を使い、中断だけを理由に全qualityへ広げず関連選択へ戻ることを確認する。失敗の原因となった変更は次回も数えられる。

関連選択は分岐点以降のcommit、staged／unstaged、未追跡、削除・改名の旧パスを含める。変更したqualityテスト自身も選ぶ。通常のファイル読込み、変数import、子プロセス・Python・生成入力は、明示した`dependencies`か`globalChanges`で補う。対応できない変更が一つでもあれば全qualityへ広げる。

Bunの標準選択が一部のテストを選んでも、すべての変更の影響を特定できたとは限らない。実行記録や明示対応等で届き先を確認できない変更が混じる場合は、全qualityへ広げる。未実行分岐等では標準CLIだけなら絞れる場合もあるが、この保守的な判定を省略しない。Bun 1.4.4では関連0件も終了0になるため、選択診断・依存記録・JUnitの有無を照合する。実際に選択されたテストの結果欠落は失敗とし、補完を含めて一件も実行されなければ成功にしない。

記録はworktree直下の`.feedback-loop-records/records.json`へ、版番号とテストごとの基点・読込みモジュールのハッシュを1つのJSONにまとめて保存する。形式は[呼出し仕様](contract.md)を使う。一時ファイルへ書いてからrenameで置き換える。中の`.gitignore`が全ファイルを除くので、対象repoの`.gitignore`は変更しない。Codexの既定のサンドボックスはGitのディレクトリを読取り専用にするため、そこへは置かない。

HEAD、実行runtime、記録器・runnerの内容、関連選択設定、package設定、lockfile、読込みモジュールのhashを照合する。現在の変更一覧へ含まれる入力は選択処理で扱い、それ以外の内容不一致や基点不明は記録を信頼しない。commit後の基点変更では全件へ広がる。失敗・取消では成功記録を部分採用せず、失敗・未完了のテストの利用中の記録を外す。親の強制終了で保存処理を実行できなかった場合は置換前の記録が残る。

記録の有効性は現在のquality候補について判定する。削除済み・assuranceへ移したテストの記録は同じJSON内に残すが、その古い基点だけで現行quality全体を無効にしない。対象外のテストをqualityへ戻した場合は、その時点で再び基点を照合する。

実行されなかった分岐、環境変数を引き継がない子、ファイル読込み等を完全追跡するものではない。担当AIはassuranceやその検証対象を変えた場合に該当テストを直接実行し、影響を判断できなければ`bun run check`など導入先の既存コマンドで全体checkを直接実行する。`test:affected`はこれらを自動実行しない。提出前・CIには全体checkを使う。

## Vitest

対象repoのローカルVitestで、公開APIの`createVitest`と`getRelevantTestSpecifications`を使い、変更ごとの関連qualityをテスト本体を実行せずに確認する。明示対応もVitestの到達先もない変更が混じれば全qualityへ広げる。実行は公開CLIの`related ... --run`を使う。既存のconfig・global setup・環境変数・codegen・DB準備を保つ。収集用コマンドは導入版の`list`の出力をrepo相対パスのJSON文字列配列へ整え、通常checkと照合する。[Vitest 5のAPI](https://v5.vitest.dev/advanced/api/vitest.html#getrelevanttestspecifications)と[CLIガイド](https://v5.vitest.dev/guide/cli.html)を導入版へ照合する。公開APIの対応が確認できない版では、正常に選択できたと扱わない。

補助スクリプトは変更テスト自身と明示した依存先を関連入力へ含め、assuranceを除外する。設定・lock・選択器・削除、依存先不明の入力は全qualityへ広げる。Vitestの関連選択はimport graphだけを追う。ファイルの読込みと子プロセスは`dependencies`で足す。`dependencies`の明示先とimportの到達先は和集合で選ぶ。到達先が0件でも、`dependencies`に当たる入力は全qualityへ広げない。JSONレポートで完了・実行集合を確認し、選択した全ファイルの結果を要求する。関連0件の終了0や、一部の結果だけの成功を全体の完了に数えない。skip等は対象repoの既存契約へ照合する。

## 導入時の確認

変更・削除・改名・未追跡、新規テスト、記録なし・破損・古い記録、設定変更、不明な入力と既知依存が混じる場合をテストへ照合する。Bunの通常実行と記録付き実行の値・assertion・成功失敗、並列の帰属も確認する。既存の保証が十分なら重複ケースを増やさない。診断・対象・再実行方法と、変更なし・候補0・選択不能・失敗・成功を区別する。

導入用設定の変更が残った実行は、通常ソース変更の絞り込みの証拠と分ける。隔離した検証用checkoutで導入後の版を比較元にし、信頼できる記録を用意してから、通常のソースだけを変更する。通常importに加え、子Bunやファイル読込みの補完対象が選ばれ、無関係なqualityとassuranceが実行されないことを実行ログで確かめる。全ソースを`globalChanges`へ指定した全件成功だけで導入完了としない。

関連選択の漏れは、次の3つの形で起きやすい。導入時に対象repoの該当箇所を探し、対応を確認する。

- `dependencies`の`inputs`へ`src/**`等の広いglobを書くと、記録にない入力まで既知の入力と扱われる。その入力を読む別のテストは選ばれず、全qualityへも広がらない。`inputs`は、対応先のテストが実際に読む範囲に限る。対応が分からない入力は`dependencies`へ入れず、全qualityへ広がるままにする。
- テストが`env`を置き換えて子Bunを起動すると、記録器を渡す`BUN_OPTIONS`が子へ届かない。子が読んだファイルは記録されず、そのテストは子の読む入力の変更で選ばれない。`env:`を指定して子プロセスを起動するテストを検索し、子へ`BUN_OPTIONS`を引き継ぐか、子が読む範囲を`dependencies`で補う。変数に入れた環境を渡す形は検索で漏れるため、子を起動するテストは本文を読む。
- `bun run test:affected`の外側のプロセスだけをSIGKILLすると、`runtime.mjs`本体とその子孫が残る場合がある。取消の確認では、`runtime.mjs`本体への取消と強制終了を対象にする。外側だけを止めた場合は、残った`runtime.mjs`とテストのプロセスを探して終了させてから、次の実行に進む。

時間を報告する場合は準備とテスト本体を分け、実行した版・対象・件数・終了状態を生ログへ残す。未実行・失敗・処理省略を高速化へ読み替えず、固定閾値や変異スコアを合否条件にしない。
