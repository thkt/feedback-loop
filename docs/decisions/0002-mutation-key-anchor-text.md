# 壊し方の鍵に、囲む関数の字を入れる

## Context and Problem Statement

動作の変わらない壊し方の記録（`.feedback-loop-mutants.json`）は、鍵と置き換える前の字（`original`）で、今の壊し方と照らす（#191、`src/mutation.ts` の `matcher`）。鍵は、パス・囲む関数の名前・関数の中の構文木の経路・規則・置き換えの hash からなる（DR-0001）。経路は、名前の付かない文を番号で指す。そのため、関数の中で文を入れ替えるか足すと、同じ鍵が別の式を指すことがある。その式の `original` が記録と同じなら、照合は一致とみなす。その式の壊し方がすり抜けても、一覧に出ない（#228）。

たとえば、関数の本体に `foo(a > 0);` と `bar(a > 0);` があり、`bar` の引数の壊し方を記録したとする。その前に文を 1 つ足すと、記録の鍵は `foo` の引数を指す。記録した `bar` の壊し方は一覧に戻り、`foo` の壊し方は記録で隠れる。記録したときと別の式の壊し方を、記録が隠さないようにする必要があった。

## Decision Drivers

- 記録が、記録したときと別の式の壊し方を隠さない
- 鍵が別の式を指しうる記録は、壊し方を隠さず、外すよう案内する
- 関数の外の変更（ほかの関数を足す、ファイルの先頭に文を足すなど）では、記録を外さない
- 記録ファイルの形と、記録する人の手順を変えない

## Considered Options

- 鍵の hash に、壊し方を囲む一番内側の名前のある関数の字を入れる
- 鍵の hash に、置き換える式を含む行の字を入れる
- 記録に、式の周りの字を持たせて照らす
- 重なる鍵を、先頭も含めて番号付きにし、番号付きの鍵を記録させない
- コードを変えず、照合の限界を文書に書く

## Decision Outcome

Chosen option: "鍵の hash に、壊し方を囲む一番内側の名前のある関数の字を入れる", because 経路はその関数から数えるので、関数の字が同じなら、同じ経路は同じ式を指すからである。関数の字が変われば鍵も変わり、記録は今の `not-generated` の経路で外れる。

- 鍵の hash は、置き換えた字と、壊し方を囲む一番内側の名前のある関数の字から作る。名前のある関数が無ければ、経路の起点になるファイルの先頭の文の字を使う
- 字は、空白とコメントを含めて、ソースのとおりに使う。改行の字だけは、`\r\n` を `\n` に揃える。Git の改行の変換で作業ツリーの改行が変わっても、鍵は変わらない
- 名前の無いファイルの先頭の文は、経路で番号（`body[0]` など）を使わずに指す。どの文かは hash に入れた起点の字で分け、字の同じ文は鍵の番号（`#2` など）で分ける。番号で指すと、前に文を足しただけで、字の同じ別の文に記録が当たる
- 鍵のほかの部分（パス、関数の名前、関数の中の経路、規則）と、記録ファイルの形と照合は変えない

### Consequences

- Good, because 関数の中の文の入れ替えと挿入で、記録が別の式に当たらない。#228 で試した 4 つの変更（文の入れ替え、文の挿入、`return false;` が並ぶ関数への挿入、字の同じ `if` 行が並ぶ関数への挿入）では、どれも記録が `not-generated` で外れた
- Good, because 起点の外を変えても、鍵は変わらない。名前の無いファイルの先頭の文も、前に文を足したときに同じ文を指し続ける。#228 で、字の同じ 2 つの `init();` の前に文を足しても、記録は同じ文に当たった
- Good, because 鍵の番号（`#2` など）は、名前と字の同じ起点どうしにだけ付く。その 2 つの起点からは同じ候補ができる。そのため、作らない候補を番号のために数える仕組み（#229）が要らなくなる
- Bad, because 関数の中を変えると、その関数の中の記録がすべて外れる。整形し直しとコメントの変更も含む。外れた記録の壊し方は一覧に戻り、動作が変わらないかを判断し直す。関数の変更で、記録した理由が成り立たなくなることもある（前の行の確かめを消すなど）ので、判断し直すことを受け入れる
- Bad, because 関数の外にある式（クラスのフィールドの初期化式など）は、ファイルの先頭の文全体が起点になる。その文の中のどこを変えても、記録が外れる
- Bad, because 名前と字の同じ起点が同じファイルに 2 つ以上あり、その並びが変わると、番号の付いた鍵が別の起点を指す。記録は別の起点の壊し方に当たる。#228 の時点で、repo の 69 ファイルに番号の付いた鍵は無い
- Bad, because すべての壊し方の鍵が変わり、今の記録はすべて外れる。mutation はまだどの版にも入っていない。版に入る前の今変えれば、版を使う導入先の記録は外れない

### Confirmation

- `tests/mutants.test.ts` が、関数の中の文の入れ替えと挿入で鍵が変わることと、起点の外の変更と改行の字の違いで鍵が変わらないことを確かめる
- 鍵が変わった記録を `stale` の `not-generated` に入れ、その壊し方を一覧に入れることは、今の `tests/mutation.test.ts` が確かめている

## Pros and Cons of the Options

### 鍵の hash に、壊し方を囲む一番内側の名前のある関数の字を入れる

- Good, because 経路の起点と同じ範囲の字を使う。名前と字の同じ起点が 2 つ以上ある場合を除き、経路が別の式を指す変更では鍵が変わる
- Bad, because 関数の中の、壊し方と関係しない行の変更でも記録が外れる

### 鍵の hash に、置き換える式を含む行の字を入れる

- Good, because 外れる記録が、変えた行の壊し方に限られる
- Bad, because `return false;` が並ぶ関数と、字の同じ `if (a > 0) {` 行が並ぶ関数では、前に文を足すと、今と同じく別の式に当たる（#228 で試した）

### 記録に、式の周りの字を持たせて照らす

- Bad, because 記録ファイルの形と、記録する人の手順が変わる
- Bad, because 周りの字をどこまで取るかは、鍵に入れるときと同じく決める必要がある

### 重なる鍵を、先頭も含めて番号付きにし、番号付きの鍵を記録させない

- Bad, because 位置で指す鍵の入れ替えと挿入（`foo` と `bar` の例）を防げない

### コードを変えず、照合の限界を文書に書く

- Bad, because すり抜けた壊し方が、記録で一覧から隠れることが残る

## More Information

- 改める決定: DR-0001 の Decision Outcome のうち、鍵の構成の項（「鍵は、パス・囲む関数・関数の中の構文木の経路・規則・置き換えの hash からなる」）。hash に、囲む関数の字を足す。DR-0001 のほかの決定は変わらないので、DR-0001 は accepted のまま残す
- 決定の出どころ: #228 の本文と、その `/scoping` での thkt の回答（2026-11-22）。回答は 2 回ある。1 回目で、関数の字を鍵に入れること、関数の中の変更で記録が外れることを受け入れることを決めた。critic-design の評価の後の 2 回目で、名前の無いファイルの先頭の文を `body` で指すこと、改行の字を揃えること、DR-0001 を accepted のまま残すことを決めた
- 試した版: 0a6d6a2（2026-11-22）。試しの実装と今の実装で、repo の 69 ファイルから作る壊し方の数と順は同じで、番号付きの鍵はどちらも 0 件だった
- critic-design の評価: weakened。名前の無いファイルの先頭の文を番号で指すと、字の同じ文の前に文を足したときに記録が別の文に当たるという指摘と、改行の字で鍵が変わるという指摘を直したうえで採る
- 実装: #228

### Reassessment Triggers

- 導入先で、関数の中の変更で外れた記録を記録し直す手間が、記録を使う利点より大きいと分かったとき。たとえば、整形し直しのたびに多くの記録が外れるとき
- 名前と字の同じ関数の中の壊し方を、記録する必要が出たとき
